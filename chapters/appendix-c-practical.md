# 实践问题

本附录覆盖规模化运行后训练实验的实践考量。
它的形式是一份经验清单，而不是连贯的叙述。

## 后训练的算力成本

后训练运行的算力成本有两种不同的界定方式。
最大的成本在**开发配方**上，它很容易达到最终几次训练运行算力的 10 倍到 100 倍。
其次是**把配方彻底跑一遍**的成本——更容易度量——它包括多个随机种子、细致的评估、潜在的工程麻烦等等。

对第一类成本：为了开发出 Tülu 3 这样的后训练配方 [@lambert2024t]，团队在 7B 规模上跑了量级为数千次的实验/评估，才得到最终模型。

对最终运行，Olmo 3 的报告详细记录了训练最终 32B Think 模型所涉及的内容 [@teamolmo2025olmo3]：

> 后训练遵循一种不同的操作模式：每个阶段我们都要跑多次，扫过学习率与其他超参。后训练（尤其是 RL）的理论发展得不够，所以我们不得不跑多个实验，才能确定给定基座模型的最优超参。我们希望在未来的工作中解决这一点。
>
> 在后训练期间，检查点评估消耗的算力占比更大，部分原因是推理模型在核心基准上生成很长。对 SFT，我们在每份 256 张 GPU 上并行扫了四个候选学习率，跑了 36 小时。然后是大约 12 小时的评估、合并与检查点确认，合计约两天。DPO 每次运行耗时更短（在每份作业 64 张 GPU 上跑完整学习率扫描约 18 小时），但实践中因集群不稳定而拖到数天。Olmo 3 Think 32B 最初的最终 RL 运行跨度约 5 天，其中至少有 1 天的训练时间因稳定性问题而浪费。Olmo 3 首次发布后，我们把最好的那次 RL 运行又继续跑了 21 天、用 224 张 GPU，才产出 Olmo 3.1 Think 32B。

随着扩展强化学习成为更标准的实践，这会再次变化 [@khatri2025art]。
接着上面的例子：Olmo 3 32B Think 原本的后训练只花了两周，而要发布改进后的 Olmo 3.1 32B Think，团队需要用 RLVR 再训练 3.5 周。这是**时间**上的可观成本，而不只是总算力上的。

## 评估的方差

后训练中一个被低估的挑战是**评估方差**，尤其随着推理模型兴起——它们需要使用大于 0 的温度采样才能拿到最佳评测分数。
只要从模型采样，输出就变得更多变。
不同基准的稳定性特征差别巨大，原因包括提示难度的方差、评测集中提示的数量、被训练模型的脆弱程度等等。

在 Olmo 3 期间，团队追踪了用于评估推理模型的不同评估的方差。
下表给出每个评估的标准差，计算方式是“14 个模型各跑 3 次的标准差”再取均值（先算每个模型的方差，再按评估平均）：

|----------|-----------|-----------|
| 高方差 | GPQA | 1.48 |
| | AlpacaEval 3 | 1.24 |
| | IFEval | 0.88 |
| 稳定 | ZebraLogic | 0.56 |
| | Omega | 0.56 |
| | AIME 24 (Avg@32) | 0.54 |

| | BigBenchHard | 0.39 |
| 非常稳定 | LiveCodeBench (Avg@10) | 0.29 |

有些评估（例如 LiveCodeBench）既有噪声又便宜（因为集合里提示少），所以对每个模型把该评估重跑 10 次，就能把它从高方差组移入稳定组。每个评估都可以这样做，但成本很容易膨胀。

我们还能看到其他方差来源：评估设置中的批大小、vLLM 内的张量并行设置（例如基线用 TP=2），以及其他在跨基础设施采样长生成时很敏感的具体数值设定。对推理模型而言，方差无处不在。

## 管理训练表现的方差

在本书讨论的所有后训练配方与工具中，最终模型的表现都存在可观的方差。
理解这个方差的分布、来源与影响，对造出强模型至关重要。
训练最终模型的目标是**采样许多点**——通过改变训练参数与随机种子——以获得尽可能强的模型。
注意这是在“模型**确实**更好”与“仅仅从评估噪声中重新掷骰子获益”之间做权衡。

上一节关注*评估*噪声，而更棘手的噪声来源是**训练不确定性**。
评估噪声可以通过在给定检查点上跑更多测试来管理（均匀地降低噪声）；但模型只被训练一次，却可以**从正向离群值中获益**。

实践中，训练团队会采取许多步骤，从配方中榨出尽可能大的价值：

1. 对每一次最终模型运行，扫核心优化值，如学习率、批大小等。例如用一个新的基座模型时，我建议先在很宽的区间上跑 10 个学习率、确认落在最优范围内，然后在更窄的最优窗口里重跑。
2. 在最好的几组设置上跑多个随机种子。随机种子对最终模型可能有实质影响，值得为它花算力。
3. **模型合并**已被确立为打造强模型的关键工具。合并有多种做法，从“合并同一数据上的不同检查点”到“合并特定领域的专精模型”。总体上，合并在最终配方中被视为一种强大而简单的工具；但关于“如何在配方中为后续合并做准备”，明确的最佳实践尚未确立 [@yadav2024matters]。

## 识别坏掉的训练任务

训练模型时，一个重要且简单的直觉是区分不同类型的问题。
你希望大部分时间花在“当前数据、算法或配方就是不够好”这类问题上。
另一方面，在搭建新配方时，也常有某些方法干脆是坏的。

理解这一点最好的办法，是在一个基本静态的评估套件上评估许多模型。
然后你会形成直觉：哪些测试很难被后训练干预推动（通常是知识密集型的评估，如 MMLU）。
当一个后训练设置里某处非常、**非常**坏掉时，这些大体稳定的评估常常会在一次训练任务中掉 10–20 分。
**这是开发工具链时最有用的信号之一！**
